# Architecture & Design Decisions — WaterScience AI Customer Support

## 1. Executive Summary & Problem Context

WaterScience customer service handles approximately **2,000 inbound interactions daily** across WhatsApp and email. The query volume spans repetitive compatibility questions, consumable cartridge lifecycle queries, installation guidance, shipping tracking, warranty claims, returns/refunds, and water quality inquiries (e.g. "Why did my TDS not drop?").

This prototype implements an **AI-augmented Agent Assist System** with **Mandatory Human Oversight** for Problem 2. It does **not** deploy an autonomous chatbot that sends unreviewed messages to customers. Instead, it classifies incoming queries, retrieves applicable evidence from a verified knowledge base, enforces deterministic safety and channel policies, drafts an evidence-grounded response, and presents the draft with audit citations to a human agent for approval or modification.

## 3. Key Design Decisions & Rationale

### 3.1 Why Deterministic Guardrails over Pure LLM Generation
- **Zero Hallucination Tolerance:** Customer service responses about warranty, refunds, hot-water limits, and water safety cannot rely on LLM temperature or probabilistic recall.
- **Strict Channel Separation:** WaterScience website orders have a 60-day return policy for CLEO, whereas Amazon and marketplace orders follow Amazon's policies. A deterministic check prevents website policies from leaking to Amazon customers.
- **Conflict Transparency:** The official SFU-717 product page specifies a **45°C maximum**, whereas the replacement cartridge FAQ specifies **60°C**. A standard LLM would pick one number arbitrarily. Our deterministic engine detects the conflict, explains both values, and creates a human escalation card citing `S01` and `S02`.
- **Explainability:** Every escalation flag, guardrail trigger, and required info checklist is generated by clear, testable Python code that any junior engineer can audit and maintain.

### 3.2 Why Lightweight Structured Retrieval instead of a Vector Database
- The current verified knowledge base comprises **11 source documents** and **6 product categories**.
- Introducing Chroma, Pinecone, or pgvector for this scale would introduce operational complexity, embedding latency, index drift, and cosine similarity threshold bugs without adding any retrieval accuracy.
- A deterministic JSON knowledge base lookup keyed on verified SKU aliases and issue categories guarantees 100% deterministic precision.

### 3.3 Mandatory Human Approval Model
- Customer trust in D2C depends on accurate after-sales support. Autonomous chatbots that promise refunds or diagnose plumbing issues create legal and brand liabilities.
- The pipeline outputs every case with `approval_status: "pending_approval"`. An agent can inspect the draft, view the supporting links, edit the message if needed, and click "Approve" with a single click, reducing agent drafting time from ~3 minutes to ~15 seconds while retaining human accountability.

### 3.4 Handling of SYN-020 (Product Identification First)
- When a customer sends a photo of an old filter without knowing the model (`SYN-020`), the system does not recommend a generic replacement cartridge (which risks leaking or thread mismatch).
- Per the prompt requirement, it sets `review_status = "needs_clarification"` and asks for product identification details (SKU label, photo of connectors, invoice) before recommending a replacement. It only escalates to manual matching if the product cannot subsequently be identified.

## 4. Latency & LLM Cost Assumptions

### 4.1 Latency Analysis
| Step | Provider: Mock Mode | Provider: Live LLM (GPT-4o-mini / Groq) |
| --- | --- | --- |
| Channel & Product Detection | < 1 ms | < 1 ms |
| Knowledge Base Retrieval | < 1 ms | < 1 ms |
| Deterministic Policy Engine | < 2 ms | < 2 ms |
| Response Generation | < 1 ms | ~450 ms (GPT-4o-mini) / ~180 ms (Groq Llama-3.3) |
| Total End-to-End Latency | **~4 ms** | **~200 ms – 500 ms** |

### 4.2 Cost Model Assumptions (at 2,000 queries/day)
- **Daily Volume:** 2,000 queries / day (approx. 60,000 queries / month).
- **Average Prompt Tokens:** ~650 tokens (retrieved facts + customer message + guardrails).
- **Average Output Tokens:** ~150 tokens (concise draft).
- **Model:** `gpt-4o-mini` ($0.15 / 1M input tokens, $0.60 / 1M output tokens):
  - Daily Input Cost: $2,000 \times 650 \times \$0.15 \times 10^{-6} = \$0.195$
  - Daily Output Cost: $2,000 \times 150 \times \$0.60 \times 10^{-6} = \$0.180$
  - **Total Cost per Day:** **~$0.38 / day** (~₹32/day)
  - **Total Cost per Month:** **~$11.40 / month** (~₹950/month)
- *Note:* These figures are engineering projections based on published pricing schemas, not measured billing data.

## 5. Failure Modes & Mitigations

1. **Failure Mode: Customer sends unparseable slang or regional language dialect.**
   - *Mitigation:* The classifier falls back to `general_inquiry` with `detected_product = None`, requests clarification, and routes to human support rather than inventing an answer.
2. **Failure Mode: LLM provider outage or rate limit (HTTP 429/500).**
   - *Mitigation:* `ResponseGenerator` wraps LLM calls in a `try/except` block and immediately falls back to the deterministic grounded mock draft.
3. **Failure Mode: Customer asks for medical advice (e.g. severe skin rash or hair loss cure).**
   - *Mitigation:* Deterministic rule intercepts medical keywords, declines hair fall guarantees, notes that filters are not medical devices, and advises consulting a dermatologist.
4. **Failure Mode: Marketplace return confusion.**
   - *Mitigation:* The engine strictly segregates Amazon/Flipkart purchases from the website's 60-day return policy.

## 6. Privacy & Data Handling Considerations

- **PII Scrubbing:** Customer names, phone numbers, and addresses in free text should be anonymized before passing to third-party LLM APIs.
- **Internal Order Verification:** Order IDs and invoices should only be validated via authenticated internal microservices, not included in raw LLM training or ungoverned corpora.
- **Audit Logging:** Every approval action records the timestamp, reviewer identity, reviewer notes, and whether the draft was edited before dispatch.

## 7. Scaling to 10× Volume (20,000 queries/day)

At 20,000 queries/day (approx. 14 queries/minute average, peaking at 80 queries/minute during peak hours):

1. **Asynchronous Task Queue (Celery / Redis / AWS SQS):**
   - Decouple webhook ingestion from LLM generation. Inbound WhatsApp messages are immediately acknowledged (HTTP 200) and queued for background drafting.
2. **Stateless Horizontally Scaled Workers:**
   - Run multiple FastAPI worker containers behind an Application Load Balancer.
3. **Database Persistence:**
   - Migrate in-memory case state to PostgreSQL / DynamoDB with read replicas for supervisor dashboards.
4. **Agent Tiering & Smart Routing:**
   - Route high-risk cases (leaks, cracks, warranty claims) to senior technical specialists, while routing routine compatibility and tracking questions to Level 1 support.
5. **LLM Semantic Caching:**
   - Cache grounded drafts for identical compatibility queries (e.g. "Will SFU-717 fit 24mm tap?") with a TTL of 24 hours, reducing LLM costs and latency by 40-50%.
